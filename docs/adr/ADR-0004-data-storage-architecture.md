# ADR-0004: 数据架构与存储扩展策略

- **状态**：已采纳（2026-08-29）
- **决策人**：Linda
- **关联**：local-dev-env（本地基础设施选型）、ADR-0002（基础设施层授权）

## 背景

ADR-0002 与 local-dev-env 已确定 Postgres + pgvector 为统一主存储，理由是跨境 ERP 的业务关系数据（订单 / 商品 / 库存）与向量检索共用一套存储，避免双写一致性问题。

但跨境 ERP 的订单、流水类表会随时间持续增长，数据量放大后必然面临两个问题：

1. **单机容量 / 写吞吐瓶颈**：单实例到顶后如何横向扩展。
2. **大表查询与维护成本**：全表扫描慢、索引膨胀、VACUUM 压力大。

在 MySQL 生态里，这两个问题往往靠"分库分表"（手工路由中间件 + 双写 + 跨分片 join 拼接）解决，工程成本高且易出错。本 ADR 明确 Liganex 在 PG 上的对等替代方案，避免重蹈手动分片的运维轮子。

## 决策

Liganex 采用"**单机分区表打底 + 连接池兜底 + 横向 Citus 收尾**"的三段式存储策略，不引入自建分库分表：

| 维度 | 决策 | 替代的 MySQL 做法 |
|---|---|---|
| 主存储 | Postgres + pgvector（业务数据 + 向量同源） | — |
| 单机大数据量 | 原生声明式分区表（Range 按时间 / List 按地区） | 按时间/业务手工分表 |
| 连接模型 | PgBouncer 连接池（必配） | 连接池（MySQL 连接模型更轻，PG 需主动补） |
| 索引策略 | BRIN（时序）/ Partial（热子集）/ GIN（JSONB·数组）+ 表空间冷热分离 | 普遍无差别 B-tree |
| 横向扩展 | 单实例到顶后上 **Citus**（自动 sharding，SQL 兼容） | 自建分库分表中间件 |
| 运维硬要求 | autovacuum 调优（大表必调） | — |

具体约定：

1. **分区表替代分库分表**：订单 / 流水按时间做 Range 分区，商品 / 库存按地区做 List 分区（跨境 ERP 天然带"时间 + 地区"维度）。分区键必须进入主键与高频查询条件，否则退化为全分区扫描。利用分区裁剪（Pruning）只扫命中分区，旧分区通过 ATTACH/DETACH 在线归档 / 冷迁移。
2. **PgBouncer 必配**：PG 每连接一进程，高并发短连接必须靠连接池补，这是 PG 相对 MySQL 连接模型的真实短板，不能省略。
3. **索引与表空间策略**：时序 / 日志类大表优先 BRIN（索引体积远小于 B-tree）；只查热子集的用 Partial Index；JSONB / 数组字段用 GIN。热表 + 热索引放 NVMe，冷历史分区挂大容量盘（表空间冷热分离）。
4. **横向扩展走 Citus**：当单实例写吞吐或容量触顶，用 Citus 做自动分片——仍是普通 SQL，按分布键自动路由，不写路由中间件、不双写、不手动拼跨分片 join。Greenplum（MPP 分析）与云托管（Aurora PG / PolarDB 存储自动伸缩）作为备选。
5. **autovacuum 调优为运维硬要求**：PG 的 MVCC 留死元组，大表必须调频、调阈值、调 cost limit，并管理事务 ID 冻结（freeze）防回卷；分区表按分区独立 vacuum/analyze，单机维护成本低。

## 理由

- **分区表覆盖 90% 的"分表"诉求**：声明式分区是 PG 内核能力，免运维路由、免双写，与分库分表的手工轮子相比一致性与工程成本都优一个量级。
- **Citus 把"分库"产品化**：真正需要横向分片时，Citus 替代自建中间件，避免路由 / 双写 / 跨分片 join 三大痛点——这正是当初选 PG 的"扩展能力"优势落地的时刻。
- **PgBouncer 是必须补的短板**：PG 连接模型是真实弱势，承认并补齐即可，不影响选型结论。
- **统一存储价值不被动摇**：即使引入 Citus 或列存，业务数据与向量仍同源，双写问题天生消失，这是相对 MySQL + 独立向量库方案的持续优势。

## 边界与触发条件

- 本 ADR 不锁定具体分区粒度（月 / 日 / 按地区枚举），实现时在 `liganex-mcp-scaffold` 或业务模块 change 中定稿。
- **触发上 Citus 的条件**：单实例已达到容量 / 写吞吐瓶颈，且分区表 + 索引 + 读写分离副本仍无法消解。在此之前不提前分片（避免过早分布式复杂度）。
- **绝不自建分库分表**：任何"手工路由 + 双写"方案都违反本 ADR，应改用分区表或 Citus。
- 列存（Citus 列存 / Hydra / pg_columnar）仅用于 OLAP 类报表查询，不用于 OLTP 主路径。

## 后果

面试被问"数据量大了怎么办 / 为什么不用 MySQL 分库分表"时，可说明：PG 分区表替代分表、Citus 替代分库、PgBouncer 补连接短板、autovacuum 运维要点，以及统一向量存储如何规避双写——展示对存储扩展路径的清晰判断，而非停留在"PG 比 MySQL 好"的笼统结论。
