# ADR-0005: Schema 迁移与版本化管理

- **状态**：已采纳（2026-08-29）
- **决策人**：Linda
- **关联**：ADR-0004（数据架构与存储扩展）、local-dev-env（容器化集成测试）

## 背景

业务表结构在迭代中必然变化：新增字段、加索引、改类型、加分区、启用扩展（如 pgvector）等。若采用以下任一做法，都会在实际开发中踩坑：

- **直接修改 CREATE TABLE 初始化 SQL**：历史结构的"真相"被覆盖，无法追溯某次迭代加的字段，且多环境重建时顺序混乱。
- **在库上手敲 ALTER 不入库**：本地 / 测试 / 生产 schema 漂移，CI 无法重建一致环境，协作时变更互相覆盖。

真实开发场景要求：把"表结构变更"当成代码一样管理——每次变更是**增量、版本化、可重复执行、可审计**的，且能在 CI 与集成测试里可靠重建一致 schema。

## 决策

采用 **Flyway**（SQL-first 版本化迁移）作为 schema 迁移工具，并约定如下：

1. **增量 ALTER，不回改历史**：每次结构变更新增一个版本化迁移文件（`V{n}__{desc}.sql`），写 `ALTER TABLE` / `CREATE INDEX` / `CREATE EXTENSION` 等增量语句；历史迁移文件只读、绝不修改。
2. **版本化 + 可重复迁移分工**：
   - **版本化迁移（`V__` 前缀）**：表结构、约束、索引等一次性顺序执行的 DDL。
   - **可重复迁移（`R__` 前缀）**：视图、函数、存储过程等内容变化即按校验和重跑的对象。
3. **纳入版本控制与 CI**：迁移文件进 git；CI 执行 `flyway migrate` 校验；集成测试经 Testcontainers 用迁移初始化 schema（与 ADR-0004 的容器化集成测试衔接，保证测试库与生产库同源）。
4. **与 ORM 分工**：Flyway 是 schema 真相源（管 DDL）；MyBatis-Plus 管 DML / 查询，禁用 Hibernate `ddl-auto=update` 之类的自动建表，避免双源冲突。
5. **种子数据分离**：测试 / 演示种子数据经独立的迁移或 Flyway `afterMigrate` 回调处理，不与结构迁移混在同一文件。
6. **回滚策略**：生产环境优先"前向补偿"（再发一个 `V` 版本 ALTER 撤销），而非依赖自动回滚；重大变更可附 undo 脚本人工执行。

## 理由

- **Spring Boot 原生集成**：项目是 Spring Boot + MyBatis-Plus，Flyway 开箱即用（`spring.flyway`），无需额外编排。
- **SQL-first 契合诉求**：用户本就要"手写 ALTER TABLE SQL"，Flyway 版本化文件正好落点，不强迫 XML / YAML 抽象（区别于 Liquibase 偏声明式的写法）。
- **可审计 / 可重复 / 可 CI**：每次变更即一个带版本与说明的 SQL 文件，天然解决环境漂移与追溯——这正是用户提出的"表结构变更需要管理起来"。
- **与分区 / 向量扩展兼容**：ADR-0004 的分区表、pgvector 扩展启用都可表达为一个迁移步骤，统一在迁移里管理，演进历史清晰。

## 边界与触发条件

- 仅管理**结构（DDL）**与必要的可重复对象；业务数据变更走应用层，不进迁移文件。
- **不混用多种迁移工具**（Flyway 与 Liquibase 不同时使用）。
- **不使用 ORM 自动建表**（`ddl-auto`）作为 schema 真相源。
- 跨大版本 Flyway 升级，或引入多数据源 / 多租户独立 schema 的迁移路径时，在实现 change 中细化（当前单库单迁移路径）。

## 后果

面试被问"表结构怎么演进 / 多人怎么协同改表 / 怎么保证环境一致"时，可说明：Flyway 版本化迁移、增量 ALTER 不回改历史、SQL-first、与 Testcontainers 集成测试联动、与 MyBatis 分工——展示对真实迭代场景下 schema 治理的理解，而非"建表后手动改"或"靠 ORM 自动建表"。
