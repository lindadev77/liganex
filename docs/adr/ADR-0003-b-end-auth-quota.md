# ADR-0003: B 端应用面授权与配额边界

- **状态**：已采纳（2026-08-29）
- **决策人**：Linda
- **关联**：ADR-0002（基础设施层轻量授权）

## 背景

ADR-0002 将"轻量授权"（单一 API Key + 工具白名单 + 审计 + 只读副本）作为当前版本的授权基线，并明确其仅覆盖**基础设施层**（MCP server / hub / studio 运行时）。

但 B 端应用面（liganex-studio 前端 + 生成后端 liganex-gen）面向**外部付费客户**，天然踩中 ADR-0002 声明的三条触发条件中的两条：

- 接入多租户（不同客户共享平台）
- 对外提供 SaaS 化访问

因此 B 端必须在 ADR-0002 之上补齐"客户级授权 + 用量配额"边界，否则单一 API Key 会让所有客户共享同一额度与数据视图，既不可计费，也存在数据串租户风险。

## 决策

在 B 端应用面引入**客户级（tenant）边界**，与基础设施层轻量授权正交：

| 维度 | 基础设施层（ADR-0002） | B 端应用面（本 ADR） |
|---|---|---|
| 身份 | 单一 API Key + 工具白名单 | 客户级 API Key（tenant-scoped） |
| 目标 | 防止未授权调用 | 隔离租户 + 控制成本 |
| 配额 | 无 | 按调用次数 / token / 生成任务数 计量 |
| 计费 | 不涉及 | 配额包 + 超额策略 |
| 数据视图 | 演示只读副本 | 租户维度数据隔离 |

B 端应用面 SHALL 具备以下能力（规划态，实现时拆分独立 change）：

1. **客户级 API Key**：每个客户独立签发，密钥与 `tenant_id` 绑定。与基础设施层共享密钥体系但作用域不同（基础设施层校验"是否合法调用"，应用层额外校验"属于哪个租户"）。
2. **用量配额**：对 AI 生成类调用（文生文 / 文生图 / 图生图 / 图生视频）按 token 或任务数计量，支持软限额（告警）与硬限额（拒绝）。
3. **配额查询接口**：客户可在「账户配额」菜单查看剩余额度、用量曲线、超限记录。
4. **配额与审计联动**：配额消耗事件进入 ADR-0002 的审计日志，便于对账与排障。

## 理由

- B 端是付费产品，没有配额就无法计费，也无法防止单个客户耗尽公共资源（影响其他客户）。
- 与 ADR-0002 正交而非替换：基础设施层不引入多租户复杂度，B 端单独处理，避免安全范围失控（呼应 platform-extensions 中"沙箱是纵深防御而非替代"的同一思路）。
- 首期仅做"客户级 + 配额"，不引入完整 OAuth 2.1（仍属 ADR-0002 的"未做"清单），保持工作量可控，把展示重点放在 Agent 与 ERP 能力上。

## 边界与触发条件

本 ADR 仅覆盖 B 端应用面的租户与配额。一旦需要以下任一项，需在 B 端补齐更细的能力（仍不强制 OAuth 2.1，除非涉及第三方委托访问）：

- 客户内细粒度权限（同租户多角色 / 多 seat）
- 按功能模块或 seat 计费
- 客户自助开通与计量账单导出

## 后果

面试被问"B 端怎么收费 / 怎么防一个客户刷爆"时，可说明：基础设施层与 B 端分层授权、配额计量方式、超限策略，以及为何暂不引入 OAuth —— 展示对 SaaS 成本结构与多租户边界的清晰判断，而非回避授权问题。
