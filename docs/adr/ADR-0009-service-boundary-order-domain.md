# ADR-0009: 服务拆分边界 — 订单领域归属与服务间调用

- **状态**：已采纳（2026-08-29）
- **决策人**：lindadev77
- **关联**：ADR-0006（模块化单体、不引入网关）、ADR-0002（基础设施层轻量授权）、ADR-0003（B 端配额）、ADR-0004（存储与分区）、ADR-0007（密钥外部化）、order-openapi-mcp-loop（端到端闭环 change）

## 背景

实现「注册登录 / 订单查询 / 开放平台应用与权限集 / MCP + skill」端到端闭环时，需要确定订单业务数据的归属与服务间调用方式。

订单数据的消费方：

| 消费方 | 形态 | 获取方式 |
|---|---|---|
| B 端前端页面 | `studio/frontend` 经 `studio/backend` | 同进程内调用（本地） |
| `liganex-mcp` | 独立部署服务，供客户端 skill 对话查询 | **必须跨进程** |
| `liganex-gen`（未来） | AI 生成时可能需要订单上下文 | 未来需跨进程 |

由于 `liganex-mcp` 是独立服务，**服务间调用不可避免**，问题只在于订单数据放在哪个进程里。

## 决策

订单**不独立部署为服务**，作为 `studio/backend` 内的**独立领域模块（order）**，通过**内部服务接口**对外提供能力；同时按「服务化就绪」约束设计，保证未来可以低成本拆为独立服务。

具体要求：

1. **模块边界**：order 模块独立包结构、独立 DTO；**不对外暴露持久化实体、内部异常与 MyBatis 对象**。
2. **接口分层**（同一份领域能力，两套入口）：
   - `/api/v1/orders/*`：面向 B 端前端，**用户会话鉴权（JWT）**
   - `/internal/v1/orders/*`：面向内部服务（`liganex-mcp`），**内部服务凭证鉴权**（服务间 API Key，经启动参数/环境变量注入，见 ADR-0007）
3. **消费方抽象**：定义 `OrderQueryClient` 接口，提供本地实现（同进程直连 service）与远程实现（HTTP + 内部凭证）两种，消费方只依赖接口，切换由配置决定。
4. **数据归属**：订单相关表独立 schema / 表前缀（`order_*`），按 ADR-0004 分区（时间 Range + 地区 List）。
5. **严禁**：`liganex-mcp` 或其他服务**直连订单库**。跨服务共享数据库是被禁止的，所有访问必须走接口。

## 理由

- **拆分动因不足**：唯一真实的拆分动因是「MCP 需要跨进程读订单」，而暴露 internal API 已能完全满足；为它多引入一个部署物、一套发布与监控，收益不抵成本（与 ADR-0006 模块化单体的判断一致）。
- **避免过早分布式化**：独立服务会引入服务发现、超时重试、链路追踪、分布式事务等成本，在仅 2 个消费方、且以查询为主的阶段，这些成本换不来对应的收益。
- **服务化就绪使拆分成本可控**：接口抽象 + DTO 隔离 + 独立包，意味着未来拆分只是「换实现 + 改调用地址」，消费方代码零改动——现在不拆，不等于将来拆不动。
- **鉴权可复用**：内部服务凭证（服务间 API Key）沿用 ADR-0002 的轻量授权思路，无需引入 OAuth 2.1 或服务网格。
- **仍落在 ADR-0006 阈值内**：部署物为 `studio/backend`、`liganex-mcp`（未来加 `liganex-gen`），共 2–3 个，未达「> 3–4 个且各自扩缩容」的网关引入阈值。

## 拆分触发条件

满足以下**任一**条件时，以独立 OpenSpec change 将订单拆为独立服务 `liganex-order`：

- 出现**第三个消费方**（如 `liganex-gen` 需要订单上下文做生成）
- 订单的**写入复杂度或流量**显著高于其余业务，需要独立扩缩容或独立 SLA
- 出现「**只要 MCP / API、不部署 B 端系统**」的客户形态——此时 MCP 依赖 `studio/backend` 在架构上不成立
- 团队按领域分工，订单需要**独立发布节奏**

拆分时的既有资产：`OrderQueryClient` 接口与远程实现、独立的 `/internal/v1/orders/*` 契约、独立的 `order_*` 表结构，均可直接迁移。

## 后果

- **需要处理跨服务调用的韧性**：`liganex-mcp` → `studio/backend` 的订单查询必须配置超时、重试与降级；订单查询失败应返回明确的错误信息，**不得拖垮 MCP server 或影响其他 tool**。
- **内部接口需要版本化**：`/internal/v1/*` 同样纳入 OpenAPI 契约管理，避免隐式约定。
- **面试叙事完整**：可以讲清「订单被两个产品面消费、拆分动因是什么、为什么现在不拆、什么条件下会拆、为拆分预留了什么」——体现的是服务边界判断力，而非盲目微服务化或一味堆单体。
