# ADR-0002: 授权范围（当前版本不实现细粒度授权）

- **状态**：已采纳（2026-08-29）
- **决策人**：Liganex 作者

## 背景

Liganex 是求职导向的实验性开源项目，需在有限时间内跑通"Agent + 跨境 ERP"的端到端链路。是否要像生产系统一样实现完整授权体系，需要权衡工作量与收益。

## 决策

**当前版本不实现**以下企业级授权能力：

- OAuth 2.1 Authorization Server
- Token Audience Binding（A 的令牌不能用于 B）
- Step-Up Authorization Flow
- 动态客户端注册、细粒度 scope

但保留以下工程底线（几乎零成本）：

| 保留项 | 作用 |
|---|---|
| `tool.annotations` 声明 readOnly / destructive / idempotent / openWorld | 让客户端自动决定是否弹确认框，既是安全也是体验优化 |
| `inputSchema` 参数校验（协议强制） | 不符合 schema 直接拒绝 |
| 单一 API Key + 工具白名单 | 约一小时工作量，替代整套 OAuth |
| 全量审计日志（一张表） | 演示与排障都依赖 |
| 演示用只读 / 影子数据副本 | 避免现场把真实 ERP 改坏 |

## 理由

- 单用户 / 单租户场景，不实现多租户授权不会构成真实风险
- OAuth 全套会吞噬约一半开发周期，且展示的是安全工程而非 Agent 能力
- MCP 协议原生 tool annotations 已覆盖"是否破坏性"判定，无需自建授权层

## 边界与触发条件

一旦满足以下任一条件，须补齐 OAuth 2.1 + scope 校验 + 写操作二次确认：

- 接入多租户
- 接入真实客户生产数据
- 对外提供 SaaS 化访问

## 后果

面试被问"这东西安全吗"时，可清晰说明：做了什么、没做什么、为什么、何时该补 —— 展示权衡能力而非回避。
