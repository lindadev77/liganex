# Design: B 端 AI 生成应用

## 在架构中的位置
Liganex 现已明确为"两层产品面"：
- **基础设施层**：MCP server、hub、studio（客户端）、skill、AI 自动化/可观测/沙箱。
- **应用层（本变更）**：面向 B 端客户的 AI 生成应用，是平台的营收面，同时也是基础设施层的消费方。

数据流：B 端客户 → studio 工作台 UI → gen 后端（模型供应商抽象 + 异步任务 + 配额）→ 供应商（Volcengine 等）；
可选回环：gen 后端 → liganex-mcp → ERP 数据，作为生成上下文。

## 模型供应商抽象层
定义统一接口，四类生成各对应一个方法：
```
generateText(prompt, template, opts)   -> TextResult
generateImage(prompt, opts)            -> ImageResult
editImage(imageRef, prompt, mask, opts)-> ImageResult
generateVideo(imageRef, motion, opts)  -> VideoResult
```
- 各供应商实现适配器；配置化静态路由（首期仅 Volcengine）。
- 首期 Volcengine 映射：文本→方舟/豆包，图像→Seedream，视频→即梦。
- 统一返回标准化结构（资产 URL、供应商、参数快照、错误码），便于前端与计费统一处理。

## 异步任务框架
生图/生视频为长任务（秒级~分钟级）。设计：
- 提交即落库并返回 `taskId`，状态机 `pending → running → succeeded/failed`。
- 执行层可用线程池/消息队列（首期单机内存队列即可，后续接 sandbox 隔离执行）。
- 支持轮询与（可选）Webhook 回调；结果资产元数据持久化，可回溯审计。

## 用量与配额（成本控制）
- 客户维度配额表：`customer_id, quota_type, monthly_limit, used`。
- 生成前预检配额，超额直接拒绝且**不调用供应商**（关键：避免成本失控）。
- 仅做用量统计与上限，不做完整计费账单（Non-goals）。

## 流式对话模块（AI 创作菜单下）
- 对话是「AI 创作」菜单下与客户的智能交互界面：文本/图片输入 → 意图识别 → 路由到生成能力或 ERP 查询（经 liganex-mcp）→ 流式返回。
- 流式传输：后端以 SSE（首选，server→client 单向、实现简单）或 WebSocket 推送 token；前端边收边渲染，支持中断/重试。
- 会话状态（多轮上下文、上传的参考图）由应用侧（liganex-studio / liganex-gen）维护，**MCP 层保持无状态**——与 baseline 的"MCP 2026-07-28 stateless core"一致：MCP 不保存会话。
- 该工作台是此前规划的"智能客服问答"（ERP 数据查询）与本次"AI 生成"两类能力的自然汇合点：同一个聊天框，既能问"美国仓库存多少"，也能说"给这个 SKU 写德语 Listing"。

## B 端客户业务系统结构（多菜单）
B 端不是单页聊天框，而是一个面向客户的**多菜单业务系统**（控制台）。`liganex-studio` 的 frontend 即该系统的前端，建议菜单结构：

```
B 端业务系统 (liganex-studio frontend)
├── 工作台首页     聚合指标：订单/库存预警/近期生成/配额剩余（卡片+图表）
├── AI 创作        流式对话模块（智能助手）+ 文生文/文生图/图生图/图生视频四类入口 + 任务列表
├── 订单管理       经 liganex-mcp 查询 ERP 订单（列表/详情/筛选）
├── 商品管理       SKU 列表/属性（生成时可在此选取 SKU 作上下文）
├── 库存管理       库存看板 + 补货建议（复用 cross-border-erp-data 口径）
├── 数据看板       销售/利润分析（margin-analysis 类能力）
└── 账户配额       订阅档位、用量统计、剩余配额、API Key 管理
```

- 流式对话是「AI 创作」菜单下的模块之一，与四类生成入口并列；它同时承载智能客服问答（ERP 查询）与 AI 生成两类能力。
- 各业务模块（订单/商品/库存/看板）统一经 liganex-mcp 读取 ERP 数据，前端不直连数据库，保证数据口径与安全边界统一。
- 账户配额菜单对接 `liganex-gen` 的用量统计与客户配额，是 ADR-0003（B 端授权/配额）的前端落点。

### 单一前端入口约束（收敛原则）
**面向客户的全部操作只收敛到一个前端应用**，即 `liganex-studio` 的 frontend（B 端业务系统）。不另起独立的客户前端、不按模块拆子域/微前端、不为单个能力（如"生成站""客服站"）单独建站。

- 原架构中的「客户端 / agent 运行时」职责也并入这一应用：客户侧的操作界面与 agent/skill 交互（流式对话、skill 触发）在同一系统内，不再设一个面向客户的独立客户端。
- 收敛理由：单一入口降低客户认知成本与维护成本，统一登录/权限/配额/审计边界；拆分只会让授权、配额、数据口径在多处重复实现。
- 内部/开发者侧工具（如 hub 管理后台、MCP server 调试台）不属于"客户操作前端"，可独立，但默认也尽量复用同一套前端壳与组件库。

## 仓库归属提议（待确认）
- **生成后端** 建议独立为业务仓库 `liganex-gen`（模型抽象、异步任务、配额、资产存储），符合"前端不单独建仓、业务模块独立仓"的约定。
- **B 端客户业务系统 UI（多菜单）** 并入 `liganex-studio` 的 `frontend/`（studio 作为 B 端门面，承载业务系统框架 + AI 创作/对话 + 订单/商品/库存/看板/账户配额模块）。
- 备选：将生成能力整体并入 `liganex-studio`（前后端同仓）。若生成后端较重、需独立伸缩，则首选分离方案。

## 与 ADR-0002 的边界澄清
- ADR-0002 的轻量授权（单一 API Key + 工具白名单 + 审计）**仅覆盖基础设施层**。
- 本 B 端应用面面向外部付费客户，需**客户级 API Key + 用量/配额控制**；这正是 ADR-0002 声明的"接入多租户/真实客户数据须补齐"的触发条件。
- 由新建 `docs/adr/ADR-0003-bend-auth-quota.md` 正式记录该边界（见 tasks）。

## 与 platform-extensions 的协同
- **可观测**：生成调用、供应商延迟、配额命中率应纳入 observability 规范（复用审计日志）。
- **沙箱**：高风险/第三方脚本类生成逻辑未来可放入 sandbox 隔离执行。
- **AI 自动化**：生成的素材可接入自动化工作流（如定时批量生成 Listing）。
